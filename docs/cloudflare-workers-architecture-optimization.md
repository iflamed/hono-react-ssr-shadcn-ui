# Cloudflare Workers Architecture and Optimization Guide

## 1. Purpose

This document describes the optimized Cloudflare edition of the Hono + React SSR template. It covers:

- the runtime and dependency upgrades;
- client-side page splitting;
- server-side route and SSR splitting;
- manifest-driven asset injection;
- the migration from Cloudflare Pages to Cloudflare Workers;
- static asset delivery and browser caching;
- dynamic SSR backed by Cloudflare D1 and Drizzle ORM;
- build, preview, deployment, and verification requirements.

The primary goal is to prevent every page, interaction, API handler, and SSR dependency from being bundled into one large browser file or one monolithic Worker module.

## 2. Target Runtime and Dependency Baseline

The optimized Cloudflare branch targets the following stack:

| Area | Target |
| --- | --- |
| Language | TypeScript 7.x |
| UI | React 19.2.x and React DOM 19.2.x |
| Application framework | Hono 4.12.x |
| Build system | Vite 8.x with Rolldown |
| Cloudflare integration | `@cloudflare/vite-plugin` 1.47.x |
| Deployment CLI | Wrangler 4.x |
| Styling | Tailwind CSS 4.x and Shadcn UI |
| Storage | Cloudflare D1 with Drizzle ORM |
| Server rendering | `@hono/react-renderer` |

Important upgrade decisions:

1. The previous Pages-oriented Hono Vite adapters were removed:
   - `@hono/vite-build`;
   - `@hono/vite-dev-server`;
   - `@hono/vite-cloudflare-pages`.
2. `@cloudflare/vite-plugin` became the single Cloudflare runtime integration.
3. Vite was upgraded to version 8 and the build uses its Environment API and Rolldown code-splitting configuration.
4. TypeScript was upgraded to version 7.
5. Axios was removed from the browser bundle. Blog mutations now use the native Fetch API.
6. The client no longer imports server rendering modules such as `@hono/react-renderer` or `react-dom/server`.
7. Blog persistence moved from Workers KV to Cloudflare D1. Drizzle ORM provides typed queries, and Drizzle Kit generates versioned SQL migrations.

## 3. High-Level Architecture

```text
Browser request
├── /static/* or another uploaded asset
│   └── Workers Static Assets
│       ├── served without invoking Hono SSR
│       └── immutable browser caching for hashed files
│
└── Page or API route
    └── Hono Worker
        ├── language and i18n middleware
        ├── route-level dynamic handler import
        ├── optional Drizzle/D1 read/write
        ├── page-level dynamic component import
        ├── React SSR
        └── HTML with exact client entry, CSS, and module preloads
```

The build produces two independent graphs:

```text
dist/
├── client/
│   ├── .vite/manifest.json
│   ├── _headers
│   ├── robots.txt
│   └── static/
│       ├── client-[hash].js
│       ├── assets/
│       └── chunks/
│
└── ssr/
    ├── index.js
    ├── chunks/
    ├── .vite/manifest.json
    └── wrangler.json
```

`dist/client` is the public asset directory. `dist/ssr` contains executable Worker modules and is not a directory of pre-generated HTML files.

## 4. Client-Side Page Splitting

### 4.1 Minimal view configuration

`src/view-loaders.ts` contains configuration only:

```ts
export const viewLoaders = {
  hello: () => import("./view/Hello"),
  blogList: () => import("./view/BlogList"),
  blogUpdateForm: () => import("./view/BlogUpdateForm"),
  blogs: () => import("./view/Blogs"),
  showPost: () => import("./view/ShowPost"),
};
```

`ViewName` is inferred from these keys in `src/view.tsx`. A new page requires only one new mapping. No manually maintained union and no manually written Vite manifest module ID are required.

The mapping key must match the page filename after case and separator normalization. For example:

```text
blogUpdateForm -> BlogUpdateForm.tsx
showPost       -> ShowPost.tsx
```

This convention allows the server to match the current view to the corresponding Vite dynamic entry automatically.

### 4.2 Client hydration boundary

The client entry is intentionally small:

```text
src/client.tsx
├── vite/modulepreload-polyfill
├── app.css
└── client/hydrate.tsx
```

`src/client/hydrate.tsx` reads `window._hono_view`, validates the view name, imports only the active page, and hydrates the explicit `#app` container.

The browser does not receive the full Vite manifest. Hydration data contains only:

- the current view name;
- page metadata;
- serialized page properties.

### 4.3 Stable shared client runtime

The client build groups the following stable packages into `react-runtime`:

- `react`;
- `react-dom`;
- `scheduler`;
- `sonner`;
- `next-themes`.

This runtime changes less frequently than application pages and can remain cached across deployments when its content hash does not change.

Small Rolldown runtime helpers are left to the bundler. They are not manually merged into a larger vendor file because their size is negligible and their import relationships are generated by Rolldown.

### 4.4 Removed global vendor bundle

The old `manualChunks` rule merged every `node_modules` dependency into one large `vendor` file. That rule was removed because it caused unrelated pages to share one oversized invalidation boundary.

The current strategy is:

- one stable React/notification runtime;
- page-specific chunks;
- shared component chunks only when actually imported by multiple pages;
- content-hashed filenames for every emitted asset.

## 5. Manifest-Driven HTML Assets

The client is built before the Worker. Its manifest is copied from:

```text
dist/client/.vite/manifest.json
```

to:

```text
src/lib/manifest.json
```

before the SSR environment is built.

`src/server/manifest.ts` performs the following operations for every SSR response:

1. Locate the client entry (`src/client.tsx`).
2. Find the current page's dynamic manifest entry by normalized view name.
3. Recursively walk the entry's `imports` graph.
4. Deduplicate JavaScript module preloads and stylesheets.
5. Return only the assets required by the current page.

This avoids both extremes:

- loading every page eagerly;
- waiting for a client-side dynamic import waterfall before downloading the active page.

If a new view key does not match its file name, SSR can still render, but the page-specific preload cannot be resolved. The naming convention is therefore a performance invariant.

## 6. Server-Side Module Splitting

### 6.1 Dynamic route handlers

`src/blog.tsx` remains a lightweight route registry. Heavy route implementations are loaded only when their route is requested:

```ts
app.get("/article/:idx", async (c) => {
  const { renderArticle } = await import("./features/blog/article-handler");
  return renderArticle(c, options);
});
```

The server feature boundary is:

```text
src/features/blog/
├── article-handler.tsx
├── editor-handlers.tsx
├── list-handlers.tsx
├── post-repository.ts
├── types.ts
└── write-handlers.ts
```

Consequences:

- `markdown-it` is loaded with article rendering rather than the Worker entry;
- `iso-639-1` is loaded with editor routes;
- slug generation and write logic are loaded only for mutation routes;
- public list routes do not load editor or Markdown code;
- API and SSR business domains remain independently cacheable Worker modules.

### 6.2 SSR runtime groups

The SSR build creates explicit shared groups for:

- the local i18n and utility runtime;
- Sonner;
- React, React DOM, and Scheduler.

Page components and route handlers remain separate chunks under `dist/ssr/chunks`.

The Worker entry therefore contains routing and orchestration code instead of all pages, all UI components, all Markdown code, and every write handler.

## 7. SSR Document and Serialization

The rendering boundary is split into dedicated files:

```text
src/server/document.tsx    HTML document structure and asset tags
src/server/renderer.tsx    Hono React renderer integration
src/server/manifest.ts     current-page asset resolution
src/server/serialize.ts    safe inline JSON serialization
src/shared/client-shell.tsx shared SSR/client providers
```

The same `ClientShell` is rendered on the server and client to reduce hydration mismatches.

Inline hydration JSON is escaped before being embedded in a `<script>` element. This prevents values such as `</script>` from prematurely terminating the script block.

## 8. Replacing Axios with Fetch

The blog editor previously imported Axios, which increased the editor chunk and introduced unnecessary transitive dependencies.

The replacement uses the browser's native Fetch API and explicitly checks `response.ok`:

```ts
const response = await fetch(url, {
  method,
  headers: body ? { "Content-Type": "application/json" } : undefined,
  body: body ? JSON.stringify(body) : undefined,
});

if (!response.ok) {
  throw new Error(`Blog request failed with status ${response.status}`);
}
```

This reduced the `BlogUpdateForm` client chunk from approximately 136 KB to approximately 92 KB before gzip.

## 9. Cloudflare Pages to Workers Migration

### 9.1 Previous Pages model

The previous architecture relied on Pages-specific build adapters and a Pages Worker output convention:

```text
dist/_worker.js/index.js
dist/_worker.js/chunks/*
```

Typical operational commands were Pages-oriented, such as `wrangler pages dev` or `wrangler pages deploy`, and the build output directory was treated as a Pages project artifact.

### 9.2 Workers model

The migration replaced the Pages adapters with:

```ts
cloudflare({
  viteEnvironment: { name: "ssr" },
})
```

Assigning the Worker to the `ssr` Vite environment integrates Worker execution with the full-stack SSR build.

The source Wrangler configuration declares:

- the Worker name;
- the TypeScript Hono entry;
- the compatibility date and `nodejs_compat` flag;
- front-of-Worker caching and cross-version cache reuse;
- the D1 database binding;
- non-secret variables;
- required secret names;
- explicit `workers_dev` and `preview_urls` behavior.

The Cloudflare Vite plugin generates `dist/ssr/wrangler.json` for the compiled Worker and automatically points its static asset directory at `dist/client`. The source `wrangler.toml` therefore does not need a manually duplicated `assets.directory` value for this build.

### 9.3 Command migration

The project scripts now use:

```text
npm run dev      -> Vite development using the Workers runtime
npm run build    -> client build followed by SSR Worker build
npm run preview  -> local preview of compiled output
npm run deploy   -> build, remote D1 migrations, then wrangler deploy
```

This replaces Pages-specific deployment commands and removes the `_worker.js` output convention.

Public SSR routes combine Hono's Cache API middleware with Workers Caching in front of the Worker. `createPublicPageCache(maxAgeSeconds, staleIfErrorSeconds)` configures the fresh TTL and the error fallback window; the latter defaults to seven days. `Vary: Cookie, Accept-Language` keeps locale variants separate. Every response without an explicit public policy—including administration pages, mutations and errors—is marked `private, no-store`.

`cross_version_cache = true` lets a newly deployed version reuse public pages created by its predecessor. If page refresh throws, times out or returns `5xx`, Cloudflare serves the last successful response during its `stale-if-error` window. A true cache miss and a response older than that window cannot fall back to stale content.

### 9.4 Static asset routing

The final Worker uses asset-first routing:

1. If a request matches a file in `dist/client`, Cloudflare serves the static asset.
2. If no static asset matches, the request is handled by the Hono Worker.

This means hashed JavaScript, CSS, and `robots.txt` do not need to execute SSR code.

## 10. Browser and CDN Caching

Workers Static Assets use ETags and revalidation by default. For fingerprinted assets, revalidating on every visit is unnecessary because a changed file receives a new URL.

`public/_headers` applies an immutable policy only to generated hashed files:

```text
/static/*
  Cache-Control: public, max-age=31556952, immutable
```

Do not apply this policy to:

- SSR HTML;
- API responses;
- unhashed mutable files;
- user-specific responses.

A `304 Not Modified` response has no HTTP body, but browser developer tools can still show response-header transfer bytes and the cached representation. With immutable hashed assets, normal repeat visits avoid this revalidation round trip entirely.

## 11. Dynamic SSR, Cloudflare D1, and Drizzle ORM

The project does not generate static HTML during the build. Routes such as `/blogs` and `/article/:idx` execute dynamically:

```text
request
-> Hono route
-> Drizzle repository
-> Cloudflare D1 binding
-> page props
-> React SSR
-> HTML response
```

The `DB` D1 database is configured as a Wrangler binding and is available through `c.env.DB`. A Drizzle client is created from that request binding; application modules do not keep a mutable database client in global scope.

`src/db/schema.ts` is the schema source of truth. Drizzle Kit writes generated SQLite migrations to `drizzle/d1`, while Wrangler records and applies those migrations to local or remote D1 databases. The blog repository uses a unique slug index, separate creation and modification timestamps, and keyset pagination based on the integer primary key.

Local development uses Wrangler's local D1 database. Run `npm run db:migrate:local` before `npm run dev`. The deployment script builds first, applies pending remote D1 migrations, and only deploys the Worker after the migrations succeed. `npm run db:migrate:remote` remains available when the schema must be updated without deploying application code. Schema migrations do not copy data from a previous KV namespace, so existing production articles require a separate one-time data import before the KV binding is removed.

## 12. Variables, Secrets, and Generated Types

The project separates public configuration from sensitive configuration:

- `BLOG_USERNAME` is a normal Wrangler variable.
- `BLOG_PASSWORD` is declared as a required secret.
- `.dev.vars` supplies secrets locally and must not be committed.
- production secrets are uploaded with Wrangler or configured in the dashboard.

After changing Wrangler bindings or variables, run:

```shell
npm run cf-typegen
```

and commit the regenerated `worker-configuration.d.ts`.

Application code should access bindings through generated `Cloudflare.Env` types instead of manually duplicating binding interfaces.

## 13. Build Orchestration

The custom Vite builder enforces deterministic ordering:

```text
1. Remove the previous dist directory.
2. Build the client environment into dist/client.
3. Copy the client manifest into src/lib/manifest.json.
4. Build the SSR environment into dist/ssr.
```

The ordering is required because the Worker embeds the client manifest used for SSR asset selection. Building the Worker before updating the manifest could cause HTML to reference stale hashed filenames.

The important output naming rules are:

```text
Client entry:    static/client-[hash].js
Client chunks:   static/chunks/[name]-[hash].js
Client assets:   static/assets/[name]-[hash][extname]
Worker entry:    index.js
Worker chunks:   chunks/[name]-[hash].js
Worker assets:   assets/[name]-[hash][extname]
```

## 14. Verified Build Characteristics

The optimized build has been verified with Vite 8.1.5.

Representative client output:

| Output | Raw size | Gzip size |
| --- | ---: | ---: |
| Client entry | 6.34 KB | 2.93 KB |
| React runtime | 223.42 KB | 68.91 KB |
| Hello page | 2.75 KB | 0.96 KB |
| Blogs page | 0.99 KB | 0.50 KB |
| ShowPost page | 34.75 KB | 12.75 KB |
| BlogUpdateForm page | 91.72 KB | 31.03 KB |

Representative Worker output:

| Output | Raw size | Gzip size |
| --- | ---: | ---: |
| Worker entry | 40.03 KB | 14.97 KB |
| React runtime | 204.11 KB | 62.59 KB |
| Editor handlers | 10.18 KB | 4.26 KB |
| Article handler | 103.17 KB | 46.29 KB |

The aggregate size of all chunks is not the amount transferred for one page. The browser receives the entry, shared dependencies, and the active page's dependency closure. The Worker runtime loads server modules according to the requested route.

## 15. Verification Checklist

Run the following before deployment:

```shell
npm run typecheck
npm run build
npm run preview
```

Verify:

- every page appears as `isDynamicEntry` in the client manifest;
- the browser client graph does not contain server renderer code;
- `/` and `/blogs` return SSR HTML;
- an article route returns SSR HTML when the D1 row exists;
- `/blog/list` returns `401` without Basic Auth credentials;
- each page preloads its own chunk rather than every page chunk;
- hashed `/static/*` responses include the immutable cache header;
- `dist/ssr/wrangler.json` points assets to `dist/client`;
- `.dev.vars` and other secret files are not tracked;
- deployment uploads both Worker modules and client assets.

## 16. Adding a New Page

1. Create the page component, for example `src/view/LoginPage.tsx`.
2. Add one configuration entry:

```ts
export const viewLoaders = {
  // existing views...
  loginPage: () => import("./view/LoginPage"),
};
```

3. Use the inferred name in a route:

```ts
app.get("/login", (c) => {
  return c.view("loginPage", {
    meta: { title: "Login" },
    props: {},
  });
});
```

No `ViewName` union or manifest module ID update is required.

## 17. Operational Constraints

- Keep view imports literal so Vite can create independent dynamic entries.
- Keep view keys aligned with page filenames.
- Do not restore a single catch-all vendor chunk.
- Do not import server modules from the client entry.
- Do not manually edit generated binding types.
- Do not cache dynamic SSR or authenticated API responses as immutable assets.
- Generate Drizzle migrations from `src/db/schema.ts` and apply them with Wrangler; do not edit an already-applied migration.
- Keep the client-before-Worker build order.
- Preview compiled output before deployment, not only the development server.
